# sdd-tdd-loop

A spec-driven + test-driven loop you run **one task at a time**.

```
/sdd-init                            →  this repo's seam profile + language skill (once)
/sdd-task new "<what needs doing>"   →  a task in .sdd-tdd/tasks.json
/sdd-spec #1                         →  tracks/<area>/: spec.md + use-cases.json
/sdd-pr loans                        →  a DRAFT PR carrying the spec, from the start
/sdd-implement <area>                →  one test per use case: red → green → refactored
/sdd-commit loans                    →  one Conventional Commit; refreshes the PR
/sdd-status                          →  where everything stands
```

Seven skills, eighteen scripts, no network, no board, no cloud CLI, no poller,
and nothing that starts by itself.

**The plugin is the process; the language lives in your repo.** Nothing here
knows xunit from pytest from `flutter test`. What test levels a repo has, and how
a test at each one is written, is two files `/sdd-init` generates *in the repo* —
because the same loop runs over a .NET API and a Flutter app, and every language
fact baked into a plugin script is a fact that's wrong in some repo that
installed it.

This descends from a board-driven plugin that ran unattended — Azure Boards work
items in, draft PRs out, a launchd poller arming the whole thing. All of that is
gone, and with it most of the configuration: a plugin that has to run with nobody
watching needs to be *told* where tracks live, what the states are and which
subagent owns which platform. A loop a human runs per task doesn't. Those are
fixed constants now.

The tradeoff is deliberate: nothing here integrates with your tracker, and
nothing starts by itself. Tasks live in one JSON file you commit.

Git is the one thing that came back, and only in the two places a human would do
it anyway: `/sdd-commit` drafts a Conventional Commit from the diff and the case
evidence, then stages the paths it named; `/sdd-pr` opens the track's PR **as a
draft before the work is done** and regenerates its body from the spec every time
a case lands. Neither merges, neither rewrites history, and no *script* in this
plugin mutates git at all — the mutating commands are issued in the conversation,
where you see `git add <paths>` before it runs.

## Install

```bash
/plugin marketplace add ~/Documents/workspace/local-plugs
/plugin install sdd-tdd-loop@local-plugs
```

## Configuration: two per-repo files, both generated

`/sdd-init` writes them, once per repo. Everything else — the layout, the states,
the phase boundaries — is a fixed constant, for the reasons under *Everything else
is fixed*.

### `.claude/sdd-tdd/seams.json` — what this repo can test

The **seam profile**: the test levels this repo has, and the marker that
recognises each one.

```json
{
  "testFilePattern": "(^|/)[Tt]ests?/|[Tt]ests?\\.cs$",
  "seams": [
    { "name": "unit",        "globs": ["*.cs"], "marker": "\\[(Fact|Theory)" },
    { "name": "integration", "globs": ["*.cs"], "marker": "WebApplicationFactory|Testcontainers" }
  ]
}
```

- **The seam names are the `Level` vocabulary** of the use-case tables, plus
  `manual`. A .NET repo keeps `unit integration golden`; a Flutter repo adds
  `widget` and `viewport-control`. `probe-test-seams.sh` reports availability per
  seam, and `build-use-cases-manifest.sh` rejects a `Level` the profile doesn't
  name — one definition, so intake and validation can't disagree.
- Resolution: `$SDD_TDD_SEAMS` → `.claude/sdd-tdd/seams.json` → a `seams` key in
  `.claude/sdd-tdd-loop.json` → the built-in table shipped in
  `templates/seams.default.json` (Dart/Kotlin/Swift, TS/JS, Python).
- A profile that exists but is wrong is a **stop**, never a silent fall-back to
  the default. That fall-back is how the original bug hid: a C# repo with a full
  xunit suite probed as *no test suite at all*, which pushed every use case to
  `manual` — a spec that validates, reads as finished, and drives nothing.
- Starter profiles for dotnet, dart-flutter, ts-node, python, jvm and go live in
  `templates/seam-profiles/`. They are starting points to **cut down**, not
  defaults: a seam nobody writes here is a level intake shouldn't promise.

### `.claude/skills/sdd-lang-<stack>/SKILL.md` — how a test is written here

A normal repo-local skill, generated by `/sdd-init` from what's actually in the
repo: where a test at each seam goes, its naming, the framework idiom, one real
example per seam, and **the exact command that runs one single test**. That last
one carries the loop: the red and green observations are the evidence this plugin
produces, and a test that only ever ran inside the whole suite can be green
because something else set the state up.

`lang-guide.sh` is how `/sdd-spec` and `/sdd-implement` find it. No guide is not a
stop — it means the conventions were inferred, and the report has to say so,
because an inferred test command and a reviewed one are indistinguishable
afterwards.

## The wiki connection

`.claude/sdd-tdd-loop.json` is **optional**, and it connects to the
[`business-wiki`](../business-wiki) plugin so `/sdd-spec` can check a requirement
against documented behaviour before writing it. (It will also carry a `seams` key,
for a repo that prefers one config file to two — the profile resolves from there
when `.claude/sdd-tdd/seams.json` is absent.)

```json
{
  "wikiRoot": "business-docs/wiki",
  "rulesRoot": "business-docs/rules",
  "wikiRequired": false
}
```

| Key | Default | What it does |
| --- | --- | --- |
| `wikiRoot` | auto-detects `business-docs/wiki` | The wiki `business-wiki` maintains. Absent and undetected ⇒ the cross-check step doesn't exist on this project. |
| `rulesRoot` | a `rules/` sibling of `wikiRoot` | The derived rules JSON, for keyed lookups. |
| `wikiRequired` | `false` | `true` makes a missing wiki a **hard stop** instead of a gap recorded in the spec — for projects whose rule is that a spec derived from code is worse than no spec. |

**With no config file at all the plugin works**: `business-docs/wiki/` is used if
it's there, and the step is skipped if it isn't. `/business-wiki:bootstrap`
creates that layout, so on a repo with both plugins installed there is genuinely
nothing to configure.

Two things are deliberately *not* silent:

- a `wikiRoot` you configured that doesn't exist warns and degrades — that's a
  typo, not a project without a wiki;
- `wikiRequired: true` with no wiki exits non-zero rather than quietly
  downgrading.

### Everything else is fixed

Not "defaulted" — fixed, with no key to change it. A knob nobody turns is a knob
that only ever produces two projects that disagree about where tracks live.

| | |
| --- | --- |
| tasks | `.sdd-tdd/tasks.json` |
| tracks | `tracks/<area>/` |
| workflow | `new → specced → implementing → verify → done`, plus `blocked` |

`verify` and `done` are two states rather than one because green tests are not a
finished feature: `/sdd-implement` stops at `verify`, and **nothing in this plugin
ever sets `done`.**

## The task store replaces the board

One JSON file, mutated only by `scripts/task.sh`:

```json
{ "version": 1, "nextId": 3,
  "tasks": [
    { "id": 1, "title": "Loan simulation clips the amount when the keyboard opens",
      "state": "specced", "area": "loan-simulation",
      "description": "…", "createdAt": "…", "updatedAt": "…",
      "notes": [ { "at": "…", "title": "sdd-spec", "text": "…" } ] } ] }
```

**Never hand-edit it**, and that's not tidiness. Two rules live in `task.sh` and
nowhere else:

- **Transitions are forward-only**, with `blocked` reachable from and back to
  anywhere. A backwards move needs `--force`. Reopening work is legitimate; doing
  it by typo isn't.
- **A state outside the workflow is an error**, including as a `list` filter.
  Filtering on a misspelled state otherwise returns zero tasks, which reads
  exactly like "nothing to do".

Notes are the channel for anything a human needs to read later: wiki findings,
why a run stopped, what a blocked case is waiting on.

### `done` is gated on the wiki, when there is one

On a project where `wiki-config.sh` reports a wiki, `task.sh state <id> done`
refuses unless the task carries a note titled `wiki-delta` — the one
`/business-wiki:harvest` leaves listing the pages it changed:

```
$ task.sh state 7 done
STOP HERE: #7 has no 'wiki-delta' note and this project has a wiki (business-docs/wiki).
  /business-wiki:harvest
Or say outright that there was nothing to register:
  task.sh state 7 done --no-wiki-delta "<why nothing changed>"
```

The waiver is recorded as a note, so skipping the closeout leaves a trail instead
of no trace. This is the one place the two plugins are wired together: without it,
the closeout is a habit that survives exactly as long as nobody is in a hurry. On
a project with no wiki (`mode=off`) the gate is absent, not merely quiet.

## What the loop actually enforces

### One table row, one test

`spec.md`'s use-case tables have **7 columns, and they're a contract, not a
style**:

```markdown
| # | Type | Level | Mode | Arrange | Act | Assert |
| --- | --- | --- | --- | --- | --- | --- |
| RF-1.1 | success | unit | red-first | minAmount=5000, amount=8000 | build() | state.hasMinError == false |
| RF-1.3 | success | manual | — | physical device, keyboard open | — | the amount is fully visible |
```

`build-use-cases-manifest.sh` parses them into `use-cases.json`. A row that
doesn't parse is a row that silently never becomes a test, so the builder
rejects: an unknown `Level`, an unknown `Mode`, `manual` with a real `Mode`, a
real `Level` with `Mode: —`, an empty `Assert`, a row that isn't 7 columns wide,
and a `## Use cases` section that yields no rows at all.

`use-cases.json` is **generated — commit it, never hand-edit it.** Rebuilding
carries forward any status the loop already recorded, so `spec.md` stays the
single source of truth.

### `Mode` picks the path, and each has its own pre-state

```
red-first          pending -> red    -> green -> refactored
characterization   pending -> pinned -> green -> refactored
```

`red-first` means the test must fail before the change. `characterization` means
green before **and** after. Both demand **two observations of the test**: `red` is
"I watched it fail", `pinned` is "I watched it pass before I touched anything".
Feeding a "don't break the other platform" case to a red-first loop asks it to
make a passing test fail, so `mark-usecase-status.sh` refuses `red` on a
characterization row and `pinned` on a red-first one, naming the one it wants.

### A case cannot go green without a prior observation

`mark-usecase-status.sh` refuses `pending -> green` on both paths. A row that goes
green with nothing observed first records a test that never proved it tests
anything.

Legal moves: the two paths above, anything `-> blocked`, `blocked -> (red |
pinned | green | refactored)`, `pending|blocked -> covered`, plus idempotent
re-asserts so a retried run doesn't die on its own progress.

### `covered` — one edit, several rows

RF-3.1 and RF-3.4 often fall to the same change, so RF-3.4 can never be observed
red on its own. That is neither a green nor a blockage, and parking it in
`blocked` makes a finished row read as "waiting on a human":

```bash
mark-usecase-status.sh <area> RF-3.4 covered --by RF-3.1
```

`--by` must name a case that has been through the loop (`green`, `refactored`, or
itself `covered`); self-reference and coverage cycles are refused. Covering a row
against a `pending` one proves exactly as much as `pending -> green` does.
`covered` is terminal, counted separately from green, and `--next` never hands one
back to the loop.

### `blocked` carries a reason

`blocked` requires `--reason <key>`: `missing-module`, `wont-go-red`,
`already-broken`, `needs-business-rule`, `dirty-worktree`, `spec-wrong`, or
`other "<text>"`. The keys map 1:1 onto `/sdd-implement`'s stop conditions, and
`status.sh` groups by them.

One number covering several opposite meanings is what made this report useless: a
track once said `39 blocked` where most rows were done and the rest were waiting
on four different things.

### A red-first row must state what it observes today

`## Falsifiability` in `spec.md`, one row per red-first case:

```markdown
| # | Currently observed | Why the assert fails today |
| --- | --- | --- |
| RF-1.2 | quiz_main_title is "Quiz" in es AND en | — IT ISN'T. This row can't fail. |
```

`validate-use-cases.sh` FAILs without it. The table above can't prove an assertion
is capable of failing, and the failure is invisible until the loop hits it: a spec
once asserted a Spanish string for a key whose value is `"Quiz"` in every locale.
Nothing about the row's shape was wrong — only the value. Writing the observed
value down next to the assertion is what makes that visible at intake.

The builder additionally **warns** on assertions that are suspicious on their face
(no comparison at all, an assert restating its own Arrange, an expected value
Arrange already sets). Warnings, not failures — the semantic question is the
human's, and a false FAIL at intake is worse than a false warning.

And one section earlier, `## Verified current state` is where the *looking* is
recorded — the falsifiability row is only its consequence:

```markdown
| # | Claim the row depends on | Observed today | Where |
| --- | --- | --- | --- |
| RF-1.2 | the title is localised per locale | "Quiz" in es AND en | l10n/app_es.arb:14 |
```

Every row cites `file:line`, and `not found` is a legal observation that routes the
row to `characterization` instead of being smoothed over. `/sdd-implement` reads
this table before writing each test, so the loop never re-discovers a value intake
already established.

### Red first, module question second

```
write the failing test  ->  observe RED  ->  does the module exist?  ->  GREEN  ->  refactor
                                             ^ only here, only if red says so
```

Writing a failing test touches no feature code, so at that moment there is
nothing to create. The question is asked only when the red is "this doesn't
compile because the module is absent" rather than "the assertion didn't hold" —
which means a `characterization` case over an existing feature never reaches it,
and neither does any case whose module is already there. When one genuinely is
missing, **the loop stops for a human**: adding a feature module is a scope
decision plus a contract delta.

### The spec can't promise tests the repo can't write

`probe-test-seams.sh` reports, per level, whether the repo *already writes tests
that way* — in the scope the work touches, not repo-wide. A monorepo-wide "some
package has goldens" is worse than useless, because the seam has to exist where
the test will be written.

`available=no` is not a veto. It means a use case at that level also introduces
that test level, which is a cost to name in `## Gaps` at intake rather than
discover at implementation time. Without this, a spec can enumerate "the amount
renders without clipping" in a package with zero golden tests — a row that looks
exactly like a real one and survives validation.

The levels it probes come from the repo's seam profile, and the probe prints which
profile it used. `NONE` under the built-in table in a repo that visibly has tests
is intake's **stop 8**: a statement about the marker table, not about the repo, and
`/sdd-init` is the fix.

### The wiki check reports locations, never verdicts

`wiki-lookup.sh <keywords>` greps the wiki's markdown and the derived rules JSON
and prints the files and lines that hit. It stops there on purpose: whether a hit
means "this already covers it" or "this contradicts what the task asks for" is a
reading the agent does with the file open. No grep can tell those apart, and a
script that guessed would be inventing the one thing this step exists to avoid
inventing.

`sdd-track-planner` then classifies each requirement **NEW** / **RELATED EXISTS** /
**POTENTIAL CONFLICT**, and a conflict is a stop — not a spec written over a
documented rule.

### The commit and the PR are drafted, then reviewed with you

Both skills run in the same order — **draft, ask, act** — because a question asked
before the draft exists has to be answered in the abstract, and most of them the
diff already answers. A draft shown first turns the exchange into review, which is
the only form in which a message gets better rather than longer.

`commit-draft.sh` reports what changed grouped by the unit a `scope` names, the
*evidence* for a type (never the verdict: `feat` vs `fix` is a claim about intent),
and the track's cases in flight with their `Assert` text — the one sentence a
subject line should come from. It flags a diff spanning two groups as a split, and
it never stages: `/sdd-commit` names explicit paths, because `git add -A` is how a
scratch file or a coverage dir ends up in history.

The PR is a **draft from minute one**, and that's the point. A PR opened at the end
is a wall of diff described from memory; a draft opened as soon as the spec exists
carries the requirements, the enumerated cases and the falsifiability entries, so a
reviewer can disagree with the *specification* while it's still cheap. This is the
one thing the ancestor plugin got for free from its board, and it's back without
the board.

Kept true is the other half: a description written once is wrong by the third
commit and nobody rewrites it. `pr-body.sh` regenerates the body from the track on
every run, between markers:

```
<!-- sdd-tdd:begin -->   regenerated wholesale, every run
<!-- sdd-tdd:end -->     everything outside survives untouched
```

Reviewer notes and screenshots go outside them and persist. And *ready for review*
is a gate, not a step: every automatable case `refactored` or `covered`, nothing
`blocked`, and the task at `verify` — `pr-body.sh` prints `ready=yes|no` with its
reason, and nothing here marks a task `done`.

## What ships

| Script | Read-only | What it does |
| --- | --- | --- |
| `task.sh` | no | The task store: `new`, `list`, `show`, `state`, `area`, `note`, `next`, `remove`. Owns the transition rule and the `done` wiki-delta gate. |
| `status.sh` | yes | Every task beside its track's case progress, with `blocked` split by reason and `covered` counted apart from green. The two drift apart in diagnosable ways — that's the point. |
| `wiki-config.sh` | yes | Is there a business wiki, and where? The plugin's only configuration. |
| `wiki-lookup.sh` | yes | Where does the wiki already mention this? Locations, not conclusions. |
| `slugify.sh` | yes | One rule for turning a title into an area slug. Folds accents via Unicode decomposition, not `iconv -t ASCII//TRANSLIT` (which renders `ó` as `'o` on macOS and yields `correcci-on`). |
| `locate-track.sh` | yes | Does a track for these keywords already exist? Reports every related track as `MATCH` / `MATCH FAMILY` / `NO MATCH`, plus each one's shape (`lean` vs `legacy`) — not just the first hit. |
| `scaffold-track.sh` | no | Creates `tracks/<area>/` with `spec.md`, `contract.md`, `CHANGELOG.md`. Emits per-platform parity columns only in a repo that actually has two native codebases. |
| `validate-spec.sh` | yes | `## Gaps` present; no `RF-N`/`AC-N` header that existed in git `HEAD` has disappeared (a renumbering, not an addition). |
| `validate-use-cases.sh` | yes | `## Use cases` present, every *declared* `RF-N` has at least one `RF-N.x` row, every row parses, every `red-first` row has a `## Falsifiability` entry. Warns when an RF's cases are all `manual`. |
| `build-use-cases-manifest.sh` | writes the manifest | `spec.md` tables → `use-cases.json`. Carries `status`, `covered_by` and `blocked_reason` across a rebuild, and reports a coverage claim left dangling by one. `--check` / `--json` don't write; assertion warnings ride inside the JSON so `--json` stays parseable. |
| `mark-usecase-status.sh` | `--next`/`--summary` are | The per-case state machine. Refuses `pending -> green`, a mode's wrong pre-state, coverage against a case that never ran, and a reason-less `blocked`. |
| `probe-test-seams.sh` | yes | What can this scope actually test? Detects each seam **named by the repo's profile** by what a test at that level unavoidably contains, and prints which profile it used. Markers found outside a test file don't count — a widget that reads `viewInsets` says nothing about whether a test can drive it. |
| `seam-profile.sh` | yes (sourced, or run to report) | Resolves and validates the seam profile, and owns the `Level` vocabulary both the probe and the manifest builder read. A malformed profile stops here rather than degrading to "this repo has no tests". |
| `detect-stack.sh` | yes | Which manifests are in this scope, and which starter profile matches. Answers *what is built here* and deliberately not *how it is tested here* — that's what `/sdd-init` reads the repo for. |
| `init-scaffold.sh` | writes the two per-repo files | Installs a validated seam profile (and the wiki keys, when there's a wiki). Idempotent, refuses to clobber without `--force`, `--list-profiles` shows the starters. |
| `commit-draft.sh` | yes | Everything a Conventional Commit message derives from: the changed files grouped by scope unit, the evidence for a type, the track's cases in flight. Reads git; stages nothing. |
| `pr-body.sh` | yes | The PR title, a `ready=yes\|no` verdict, and a body rendered from `spec.md`, `use-cases.json` and the commit list, fenced by markers so a reviewer's own prose survives an update. |
| `lang-guide.sh` | yes | Where is this repo's language guide? One deterministic answer, so a missing guide is reported rather than silently replaced by generic ecosystem knowledge. |

`_common.sh` and `_confirm.sh` are **sourced, not executed**: the fixed layout,
the fixed workflow and one resolution path for `REPO_ROOT`/`CONFIG` in the first;
the shared confirmation gate in the second. The test suite asserts no other
script re-derives `REPO_ROOT` — the ancestor plugin had two implementations of
one such question that disagreed on an edge case, and it was a real bug.

### One agent: `sdd-track-planner`

Intake runs as an agent, not as plan mode in your conversation. `/sdd-spec` resolves
which task is meant and then hands the whole of it over — locate or create the track,
read what the wiki lookup names, probe the seams where the test will actually be
written, and **open the ARB / constant / provider behind every red-first assertion** —
then write `spec.md`, the use-case tables, the `## Falsifiability` section and
`use-cases.json`.

That last item is why it's an agent. A red-first row is a claim that the code today
contradicts the assertion, and the only way to know is to read the value. It's a lot of
file reading whose *conclusions* are what matters, so it happens in the agent's own
context and comes back as a report with `file:line` citations for every observed value.
The agent writes inside `tracks/<area>/` and nowhere else — not a stub, not a test — and
it doesn't spawn anything further, because a citation relayed through a nested agent is
a citation nobody read.

A stop comes back as `STOPPED: <condition>` on the first line, with the reason already
noted on the task, and `/sdd-spec` relays it rather than working around it. If the agent
can't be spawned at all, the fallback runs inline and stamps the note `planned_by: hand`
— output the main loop wrote carefully and output the agent produced are otherwise
indistinguishable, and everything downstream trusts both equally.

## No TTY needed, ever

The scripts are driven by an agent, and **an agent's Bash has no TTY**, so a
`read` prompt can never be answered — it just stalls the run and ends with the
agent asking you to paste a shell command. Every gate detects the missing TTY,
prints `[no-tty] proceeding: <action>`, and continues. The human gate lives one
level up: each `SKILL.md` says what to report before crossing one.
`SDD_TDD_ASSUME_YES=1` turns the gates into logged auto-yeses for a caller
driving these from a script of their own.

## Tests

```bash
bash test/run-tests.sh              # 441 assertions, no network
bash test/run-tests.sh task wiki    # only matching groups
```

Every test runs in a throwaway sandbox pointed at by `CLAUDE_PROJECT_DIR` and
`SDD_TDD_CONFIG`, so nothing touches the checkout it runs from. The `hygiene`
group asserts the thing that defines this plugin: no `az`/`curl` call anywhere,
git read only in the four scripts declared to read it, and **no script** that
mutates git or calls `gh` — those commands belong to the two skills, one visible
command at a time. The
`task-store` group asserts that a config file **cannot** bend the workflow — the
whole point of collapsing the configuration is that two projects can't disagree
about what `specced` means.

## Known limits

- **Nothing polls, and nothing chains.** Every run is a command you type, and
  `/sdd-implement` loops over use cases, never over tasks. That's the cost of
  dropping the board; the mitigation is that `/sdd-status` tells you in one line
  what's waiting.
- **`validate-use-cases.sh` is structural, not semantic.** It checks that cases
  were enumerated, not that they're the *right* cases. Nothing here can tell a
  thorough table from a plausible-looking one.
- **The git half stops well short of a workflow.** `/sdd-commit` and `/sdd-pr`
  commit, push and keep a draft PR current; they don't create branches, merge,
  rebase, or manage a stack. Standing on `main` with work to push is a stop, not
  something either skill fixes for you.
- **`/sdd-pr` needs `gh` and a remote.** Both absent is a stop with a one-line
  reason. The body generator is offline and works anyway, so `pr-body.sh` is still
  useful as a description you paste yourself.
- **A PR body update is a splice, and a hand-rewritten body defeats it.** If the
  markers are gone, `/sdd-pr` appends rather than overwrites and says so — it will
  not reconstruct what someone replaced.
- **One task store file.** Two people running `/sdd-spec` on different tasks at
  the same time will conflict in `tasks.json`. It's one file on purpose — every
  interesting question is a query across all tasks — and that's the price.
- **The wiki check is a keyword grep, not a semantic search.** A rule documented
  in words that don't overlap your task's words won't be found, and `NO HITS`
  means "not found by these keywords", not "undocumented". Pick keywords the way
  the wiki would phrase them.
- **The seam probe is only as good as the repo's profile.** Out of the box it
  knows Dart/Kotlin/Swift, TS/JS and Python; anything else reads `available=no`
  everywhere until `/sdd-init` writes a profile. That's a per-repo file by design,
  but it does mean a fresh install in a new ecosystem has one setup step, and
  skipping it produces an all-`manual` spec rather than an error.
- **A profile is per repo, probed per package.** In a monorepo, seam names are
  shared across stacks and the globs/markers are unioned, so `unit available=yes`
  in one package says nothing about another — always probe the scope the task
  touches.
- **The language guide is prose, and nothing validates it.** A stale test command
  in it will be trusted by `/sdd-implement`. Re-run `/sdd-init` when the test
  setup changes.
- **The layout is fixed.** A project that already keeps specs somewhere other
  than `tracks/` has to move them or fork the plugin. That's the direct cost of
  the simplification, and it's the right trade for one team, the wrong one for a
  marketplace of strangers.
- **`/sdd-implement` writes app code.** Intake writes only specs; the loop, by
  definition, changes the tree. It never edits `spec.md`, `contract.md`,
  `CHANGELOG.md` or `use-cases.json`, and it stops rather than adding a feature
  module.
- **Running the app and the manual cases stay human.** Green tests are not a
  finished feature, so nothing here sets `done`.
